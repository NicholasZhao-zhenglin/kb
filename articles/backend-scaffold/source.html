一句话：它是一个知识库服务的骨架——把文档收进来、存起来、检索出去。技术选型已经替你把「存哪儿、怎么异步、怎么迁移」这些决定做完了。

关注点选型为什么是它

这条命令能跑通，就说明 core 是干净的。跑不通（比如报要 fastapi）就说明地基里混进了上层依赖。

3. 一次请求的完整旅程

以 GET /api/health/db 为例，从网卡到响应的完整链路：

浏览器
  │  HTTP/1.1  GET /api/health/db
  ▼
uvicorn（ASGI 服务器，监听 127.0.0.1:8000）
  │  把原始 socket 字节解析成 ASGI 的 scope + receive/send 可调用对象
  ▼
Starlette 路由匹配（FastAPI 构建在 Starlette 之上）
  │  逐层匹配：外层 prefix="/api" + router.prefix="/health" + path="/db"
  ▼
依赖解析：函数签名里写了 session: DbSession
  │  = Annotated[AsyncSession, Depends(get_session)] → 调用 get_session()
  ▼
get_session() 进入 async with AsyncSessionLocal() as session
  │  执行到 yield session → 把 session 交给路由函数
  ▼
health_db(session) 执行 await session.execute(text("SELECT 1"))
  ▼
返回 HealthStatus 对象 → 按 response_model 校验 → 序列化成 JSON
  ▼
get_session() 的收尾：async with 退出 → session.close() → 连接归还连接池
  ▼
uvicorn 把 JSON 字节写回 socket

这张图里最容易被忽略的是倒数第二步：get_session 是「生成器依赖」，FastAPI 会在响应发出之后才回到 yield 下面继续执行。这保证了「一个请求一个 session，用完必定归还」——哪怕路由函数中途抛异常也一样，因为 async with 有 finally 语义。

4. 启动链：app 实例是怎么诞生的

# app/main.py
def create_app() -> FastAPI:
    configure_logging()
    logger = get_logger(__name__)

    app = FastAPI(title=settings.app_name)
    app.add_middleware(CORSMiddleware, allow_origins=settings.cors_origin_list, ...)
    register_exception_handlers(app)
    app.include_router(health.router, prefix="/api")

    logger.info("app initialized with settings: %s", settings.app_name)
    return app

app = create_app()

当你敲 uv run uvicorn app.main:app 时，uvicorn 实际做了三件事：

  1. import app.main 模块——模块级代码被执行，于是最后那行 app = create_app() 跑完
  2. 取模块里的 app 属性——这就是 app.main:app 里冒号的含义：模块路径:变量名
  3. 把它当 ASGI 应用，开始 listen 端口

所以「app.main:app 里的 app 是什么」是个很实在的问题：它是模块被 import 时的副作用产物，不是 uvicorn 构造的。

为什么用工厂函数，而不是直接 app = FastAPI()

收益说明
可测性create_app() 每次返回全新实例，测试之间互不污染
可注入可以在建实例时换上测试库的连接串、关掉 CORS
副作用集中日志、中间件、异常处理器、路由都在这一个函数里，读一遍就知道应用长什么样

同一个思路也用在 get_settings() 上的 @lru_cache：生产环境要单例（避免两份配置不一致），测试环境要能重置。

注意一个容易踩的细节：get_settings.cache_clear() 只影响后续的 get_settings() 调用。已经执行过 from app.core.config import settings 的模块，手里那份引用不会变。

所以测试里换配置，更可靠的做法是依赖注入（app.dependency_overrides），而不是清缓存。

这里已经埋了一个坑：仓库根下现在没有 .env 文件。而 pydantic-settings 的 env_file 指向不存在的文件时不报错，直接使用字段默认值。

也就是说：你现在跑的是源码里写死的默认值——包括那两个腾讯云 COS 密钥。

而且必须顺带删掉 config.py 里的明文默认值——否则「移走」是假的，密钥还在源码里躺着。可以改成空字符串，让 cos_configured 自然变成 False。

@property：派生配置

@property
def cos_configured(self) -> bool:
    return bool(self.cos_secret_id and self.cos_secret_key and self.cos_bucket)

@property
def cors_origin_list(self) -> list[str]:
    return [o.strip() for o in self.cors_origins.split(",") if o.strip()]

@property 是计算属性：不占存储、每次访问时现算、只读。这里用了两次，各有理由。

cos_configured 把「三个字段是否都非空」这个判断收敛到一处。调用方只写 if not settings.cos_configured，不用三处重复写 and 链。以后加第四个字段，也只改一个地方。

cors_origin_list 解决的是「书写习惯」与「API 要求」的错位：.env 里一行写 CORS_ORIGINS=http://a.com,http://b.com 最自然，但 FastAPI 的 allow_origins 要的是 list[str]。这个 property 就是那个转换器。

这里有个真实存在的类型标注问题：cors_origins 被标成了 list[str]，但它的实际值是字符串，后面还调了 .split(",")。

现在靠默认值是字符串所以能跑。但哪天你在 .env 里写 CORS_ORIGINS=["a","b"]，pydantic 会真的给你一个 list，.split 立刻炸。类型注解应该改成 str。

lru_cache 单例

@lru_cache(maxsize=1)
def get_settings() -> Settings:
    return Settings()

settings = get_settings()

lru_cache(maxsize=1) 表示「第一次调用后把结果缓存起来，之后直接返回同一个对象」。

为什么需要它：Settings() 每次构造都要读文件、逐字段解析、跑校验。如果每个模块 import 时都 new 一个，一是重复开销，二是可能得到两份状态不一致的配置（比如中途 .env 被改了）。

settings = get_settings() 是模块级实例，别人 from app.core.config import settings 拿到的是同一个对象。

6. core/logging.py —— 统一日志

它干什么：让全项目所有模块用同一套格式、同一个级别、同一个输出口，并且接管 uvicorn 自带的日志配置。

_LOG_FORMAT = "%(asctime)s | %(levelname)-8s | %(name)s | %(message)s"
_DATE_FORMAT = "%Y-%m-%d %H:%M:%S"

_configured = False

def configure_logging() -> None:
    global _configured
    if _configured:
        return
    handler = logging.StreamHandler(sys.stdout)
    handler.setFormatter(logging.Formatter(fmt=_LOG_FORMAT, datefmt=_DATE_FORMAT))
    root = logging.getLogger()
    root.handlers.clear()
    root.addHandler(handler)
    root.setLevel(settings.log_level.upper())

    for noisy in ("uvicorn", "uvicorn.error", "uvicorn.access"):
        logging.getLogger(noisy).handlers.clear()
        logging.getLogger(noisy).propagate = True

    _configured = True

def get_logger(name: str) -> logging.Logger:
    return logging.getLogger(name)

四个设计点，每个都对应一个真实问题：

设计不这么做会怎样
_configured 幂等闸测试里连续建 10 个 app 就挂 10 个 handler，每条日志打印 10 遍
root.handlers.clear()保证「只此一个」输出口，避免重复打印
接管 uvicorn 三个 loggeruvicorn 启动时自带一套 handler，会导致 access log 和业务日志格式不一致
输出到 sys.stdout12-factor 惯例：日志不自己管文件轮转，交给容器 / 系统采集

get_logger 为什么还要包一层

现在看它就是 logging.getLogger 的别名，像是多余。但这是留接口：日后要换成 structlog、要注入 trace_id、要加敏感信息脱敏过滤器时，只要改这一个函数，全项目几十个调用点不用动。

这是个很划算的薄封装——成本三行，收益是「未来某天的一次重构不用全项目替换」。

7. core/exceptions.py + api/error_handlers.py —— 异常体系

这两个文件是一对：一个定义「错什么」，一个负责「怎么告诉客户端」。

# core/exceptions.py
class AppException(Exception):
    code: str = "internal_error"
    message: str = "服务器内部错误"
    http_status: int = HTTPStatus.INTERNAL_SERVER_ERROR

    def __init__(self, message: str | None = None, *, code: str | None = None) -> None:
        if message is not None:
            self.message = message
        if code is not None:
            self.code = code
        super().__init__(self.message)

class NotFoundException(AppException):
    code: str = "not_found"
    message: str = "资源未找到"
    http_status: int = HTTPStatus.NOT_FOUND

这个写法有四层讲究：

  1. 用类属性承载默认值。NotFoundException 只声明三个类属性就完成定制，子类完全不用写 __init__。这是声明式写法，比每个子类重复一遍构造参数干净得多。
  2. 用 if message is not None 而不是 self.message = message or self.message。因为空字符串 "" 是合法输入，用 or 会被当成 falsy 吞掉。这个细节很多人写错。
  3. super().__init__(self.message)。让 str(exc) 有内容，否则 logger.exception 打出来是空白。
  4. 单独一个 * 强制关键字传参。NotFoundException("找不到") 可以，但 NotFoundException("x", "code") 会报错——防止位置参数传错顺序。
# api/error_handlers.py
async def _app_exception_handler(_: Request, exc: AppException) -> JSONResponse:
    return JSONResponse(
        status_code=exc.http_status,
        content={"code": exc.code, "message": exc.message},
    )

async def _unhandeled_exception_handler(request: Request, exc: Exception) -> JSONResponse:
    logger.exception("unhandled_exception at %s %s", request.method, request.url.path)
    return JSONResponse(
        status_code=500,
        content={"code": "internal_error", "message": "服务器内部错误"},
    )

def register_exception_handlers(app: FastAPI) -> None:
    app.add_exception_handler(AppException, _app_exception_handler)
    app.add_exception_handler(Exception, _unhandeled_exception_handler)

三个要点：

① 两个 handler 有明确分工。AppException 是「预料之内的错误」——业务代码主动抛，信息可以直接给用户看。Exception 是兜底的——绝不能把原始异常信息吐给客户端（可能含 SQL 语句、文件路径、连接串），只记日志、返回统一话术。

② 兜底 handler 必须有。没有它，任何未捕获异常都会让客户端收到 uvicorn 的纯文本 traceback——既是信息泄露，前端也无法统一处理。

③ 注册顺序无关。add_exception_handler 是按类型精确匹配的，不是「先注册先命中」。Starlette 会沿异常的 MRO 往上找注册过的 handler，所以 NotFoundException 自然命中 AppException 那一条。

实测踩到的坑：这个文件里定义的函数叫 register_exception_handlers，但 main.py 里曾经调用的是 register_error_handlers——少了一个 exception 词。直接 AttributeError。

这类「名字对不上」是新手最高频的错误类型，而且纯字符串层面，IDE 不一定提示。防御手段见第 15 章第 ③ 条。

8. db/base.py + db/session.py —— 数据访问底座

base.py：三行，但它是整个 ORM 的锚点

class Base(DeclarativeBase):
    pass

所有模型都会写成 class Document(Base)。对比 SQLAlchemy 1.x：

版本写法差别
1.xBase = declarative_base()函数返回动态生成的类，类型检查器看不懂
2.0class Base(DeclarativeBase)真正的类，IDE 能补全 Base.metadata，mypy 能检查

session.py：引擎与会话

engine: AsyncEngine = create_async_engine(
    settings.database_url,
    echo=False,
    pool_pre_ping=True,
)

AsyncSessionLocal: async_sessionmaker[AsyncSession] = async_sessionmaker(
    bind=engine,
    expire_on_commit=False,
    autoflush=False,
)

async def get_session() -> AsyncGenerator[AsyncSession, None]:
    async with AsyncSessionLocal() as session:
        yield session

这些参数不是抄来的，每个都有理由：

参数作用不设会怎样
pool_pre_ping=True从池里取连接前先 ping 一次，断了就换一条数据库重启或网络抖动后，前几个请求全报 connection closed
echo=False不打印每条 SQL生产日志被 SQL 淹没
expire_on_commit=Falsecommit 后不把对象字段标记为过期commit 后再读属性会触发新的 SELECT（隐性 N+1），异步下还可能报 MissingGreenlet
autoflush=False查询前不自动 flush出现难以预测的隐式 INSERT，调试很痛苦

get_session 的三个层次：

  1. async with 保证无论正常返回还是抛异常，session 一定会关闭。注意这里归还的是「连接池里的连接」，不是关掉 TCP。
  2. yield 把它变成 FastAPI 的生成器依赖——请求进来前执行 yield 之前，响应发出后执行 yield 之后。
  3. AsyncGenerator[AsyncSession, None] 的类型注解，让 DbSession 那个 Annotated 能推导出正确类型。

expire_on_commit=False 的代价要知道：commit 之后对象里的数据是快照，不再自动从库刷新。如果你依赖「commit 后重新读能拿到数据库算出来的值」（比如触发器改的字段、自增主键），需要手动 await session.refresh(obj)。

+asyncpg 这个后缀不能少

database_url 写的是 postgresql+asyncpg://…。这个 +asyncpg 决定用哪个驱动：

URL 形式驱动行为
postgresql://psycopg2同步，会阻塞事件循环
postgresql+asyncpg://asyncpg异步，原生协程

好消息是这里不会静默出错：create_async_engine 拿到非异步驱动会在启动时直接报错（要求使用 async driver）。属于「早失败」的设计，比悄悄退化成同步阻塞好得多。

9. api/deps.py —— 依赖注入

整个文件只有一行：

DbSession = Annotated[AsyncSession, Depends(get_session)]

但它把三层东西缝在了一起。用起来是这样：

@router.get("/db")
async def health_db(session: DbSession) -> HealthStatus:
    ...

FastAPI 看到参数类型标注里藏着 Depends(get_session)，就会自动：

  1. 调用 get_session() 拿到生成器
  2. 进场（执行到 yield），把 yield 出来的 AsyncSession 塞进参数
  3. 函数执行完，退场（继续执行 yield 之后的清理代码）

为什么值得为这一行单独建个文件：

收益说明
函数签名即声明路由函数不需要知道 session 从哪来，只声明「我需要一个 session」
可整体替换测试时 app.dependency_overrides[get_session] = fake，一行换掉真实数据库，不用动任何路由代码
避免重复不用在每个路由上写 session: AsyncSession = Depends(get_session)

Annotated 的价值：把「类型」和「注入指令」合并到一个名字里。没有它就得写 session: AsyncSession = Depends(get_session)——默认值的位置被占用了，这个参数就再也没法有别的默认值，而且每个调用点都要重复写一遍完整表达式。

更本质地说，这是「依赖倒置」的落点：路由依赖抽象（DbSession 这个名字），不依赖具体构造方式。

这正是 FastAPI 相对 Flask 最大的体验差异。Flask 里你会写 g.db = connect() 或者用 before_request 钩子，靠约定和全局变量传递资源；FastAPI 靠函数签名显式声明。后者的可测试性高一个量级。

10. storage/cos_client.py —— 外部服务封装

它干什么：把腾讯云 COS 的 SDK 包成「符合本项目口味的对象」，让业务代码见不到 SDK 细节。

class CosClient:
    def __init__(self) -> None:
        if not settings.cos_configured:
            raise ConfigurationError("腾讯云COS未配置")
        config = CosConfig(Region=settings.cos_region,
                           SecretId=settings.cos_secret_id,
                           SecretKey=settings.cos_secret_key)
        self.client = CosS3Client(config)
        self.bucket = settings.cos_bucket

    async def ping(self) -> bool:
        loop = asyncio.get_event_loop()
        try:
            await asyncio.to_thread(self.client.head_bucket, Bucket=self.bucket)
            return True
        except (CosServiceError, CosClientError) as exc:
            logger.warning("COS ping failed: %s", exc)
            return False

_cos_client: CosClient | None = None

def get_cos_client() -> CosClient:
    global _cos_client
    if _cos_client is None:
        _cos_client = CosClient()
    return _cos_client

三个关键决策，都值得理解：

① 为什么必须 asyncio.to_thread

腾讯云 SDK 是同步的——head_bucket 内部走 requests，会阻塞当前线程。在 async 函数里直接调用它，会卡住整个事件循环，同一进程里所有并发请求一起等。

asyncio.to_thread 把它扔进线程池执行，事件循环继续接别的活。

这是异步项目接同步 SDK 的通用解药。任何「async 函数里调同步阻塞库」的地方都要这么处理——pymysql、boto3、requests、PIL 全都算。

② 懒加载 + 模块级单例

_cos_client 是模块级私有变量，get_cos_client() 第一次被调用时才真正构造。

好处是：进程启动时不连 COS。如果密钥填错或网络不通，服务照样能起来，只是 /health/cos 报 error——而不是整个后端起不来。

这体现了一条运维原则：依赖的失败不应该阻止进程启动。否则一个次要依赖抖动就会引发服务雪崩。

③ 抛 ConfigurationError 而不是 RuntimeError

构造失败时抛的是项目自己的异常类型，它会被全局 handler 转换成 503 + {"code":"configuration_error"}，前端能识别并给出准确提示。抛裸的 RuntimeError 就只能落进 500 兜底，前端只知道「服务器错误」。

11. api/routes/health.py —— 路由与探活

router = APIRouter(prefix="/health", tags=["health"])

HealthStatusValue = Literal["ok", "error", "not_configured"]

class HealthStatus(BaseModel):
    status: HealthStatusValue
    detail: str | None = None

@router.get("", response_model=HealthStatus, operation_id="health_check", summary="健康检查")
async def health() -> HealthStatus:
    return HealthStatus(status="ok", detail="服务运行正常")

@router.get("/db", response_model=HealthStatus, operation_id="health_check_db")
async def health_db(session: DbSession) -> HealthStatus:
    try:
        result = await session.execute(text("SELECT 1"))
        result.scalar_one()
        return HealthStatus(status="ok", detail="数据库连接正常")
    except Exception as e:
        logger.exception("数据库健康检查失败")
        return HealthStatus(status="error", detail=str(e))

路径是怎么拼出来的

main.py 里写了 app.include_router(health.router, prefix="/api")，路由文件里又写了 APIRouter(prefix="/health")，加上 @router.get("/db")——

"/api"  +  "/health"  +  "/db"   =   GET /api/health/db

三层拼一层。很多人找不到路由就栽在这里：只看了路由文件，忘了 include_router 那层还加了前缀。

"" 和 "/" 的区别：@router.get("") 配 prefix="/health" 得到 /api/health；写成 @router.get("/") 会得到 /api/health/——带尾斜杠。FastAPI 会对不匹配的那个发 307 重定向，而前端 fetch 遇到重定向有时会丢掉请求体。这是个能坑半天的细节。

探针的层次感（这个文件最有价值的设计）

端点探什么它挂了意味着
GET /api/health进程活着、能返回响应进程死了，或端口不通
GET /api/health/db真发一条 SELECT 1数据库不可用，或连接串配错
GET /api/health/cos真做一次 head_bucketCOS 密钥错 / 桶不存在 / 网络不通

关键区别：/health 只证明「Web 层活着」，它不碰任何外部依赖。所以正确的用法是——

  • liveness probe 挂 /health：别让数据库抖动把好 Pod 杀掉重启
  • readiness probe 挂 /health/db：依赖没好就不接流量

这是探针设计的基本功。把两者混成一个端点，会导致「数据库慢 → Pod 被判定死亡 → 重启 → 数据库更慢」的死亡螺旋。

response_model + Literal 的配合

Literal["ok", "error", "not_configured"] 把状态值限死在三个，收益是双向的：

  • 写代码时 HealthStatus(status="okay") 会被 IDE 直接标红
  • /docs 里这个字段会渲染成下拉枚举，而不是自由文本输入框

为什么健康检查内部吞异常、返回 200 + status=error

不抛异常是有意的：HTTP 200 表示「检查执行了」，body 里的 status 才表示「结果好不好」。如果抛异常变成 503，监控系统就得分两个地方（状态码 + body）才能区分「服务挂了」和「数据库挂了」。

但也存在另一派做法：探针直接返回 503，让负载均衡器不用解析 body 就能摘流量。两种都对，关键是团队内要统一，别一半一半。

另一个要注意的点：detail=str(e) 会把原始异常信息暴露给调用方。如果 /docs 只在内网开放，无所谓；如果对公网可达，这里可能泄露连接串。生产环境建议把 detail 收敛成固定的分类文案。

第三部分 · 迁移与工程化

12. Alembic —— 数据库版本控制

它解决什么问题：数据库表结构一定会变。你需要一套「可回滚、可审计、能同步到所有环境」的机制。手写 ALTER TABLE 并记在文档里，三个月后必然对不上。

三个核心概念

概念是什么
alembic.ini配置文件，主要告诉它脚本目录在哪
alembic/env.py迁移的执行入口——定义「怎么连数据库」和「表结构从哪来」
alembic/versions/*.py每个迁移一个文件，含 upgrade() 和 downgrade()

env.py 里真正重要的只有两行

config.set_main_option("sqlalchemy.url", settings.database_url)
target_metadata = Base.metadata

第一行：把连接串从 Settings 取过来，覆盖 alembic.ini 里的。这样数据库地址只有一个来源（.env），不会出现「应用连 A 库、迁移改 B 库」的事故。

alembic.ini 里那行 sqlalchemy.url = driver://user:pass@localhost/dbname 就是个占位符，不用管它。

第二行：target_metadata 是 --autogenerate 的对照基准。Alembic 会拿它和真实数据库的 schema 做 diff，自动生成迁移脚本。

由此产生一条硬依赖：必须让 env.py import 到所有模型。否则 Base.metadata 里没有你的表，--autogenerate 会生成一个「删掉所有表」的脚本——这是 Alembic 最危险的事故。

标准做法是在 app/db/base.py 末尾集中 import，让「导入模型」这件事有唯一的落点：

# app/db/base.py
class Base(DeclarativeBase):
    pass

# 让 Alembic 能「看见」所有模型；只 import 不调用
from app.models.document import Document   # noqa: E402,F401
from app.models.chunk import Chunk         # noqa: E402,F401

为什么 env.py 必须是 async 版本

因为你的驱动是 asyncpg。同步的 Alembic 连不上 postgresql+asyncpg://。所以 env.py 里是这么写的：

async def run_async_migrations() -> None:
    connectable = async_engine_from_config(
        config.get_section(config.config_ini_section, {}),
        prefix="sqlalchemy.",
        poolclass=pool.NullPool,
    )
    async with connectable.connect() as connection:
        await connection.run_sync(do_run_migrations)   # ← 关键的一行
    await connectable.dispose()

def run_migrations_online() -> None:
    asyncio.run(run_async_migrations())

connection.run_sync(do_run_migrations) 是那座桥：Alembic 内部的迁移逻辑是同步的（它要执行任意 SQL），run_sync 让它在一个绿色线程里以同步风格操作这个异步连接。

poolclass=pool.NullPool 也是有意为之：迁移是一次性任务，不需要连接池。用完即断，避免在 versions/ 里留下悬挂连接。

常用命令

uv run alembic revision --autogenerate -m "create documents"   # 生成迁移（必须人工检查）
uv run alembic upgrade head                                    # 应用到最新
uv run alembic downgrade -1                                    # 回滚一步
uv run alembic current                                         # 当前版本
uv run alembic history                                         # 全部历史

--autogenerate 生成的文件必须人工读一遍。它在这些场景下会出错：

  • 字段重命名——会被当成「删一个、加一个」，数据全丢。必须手改成 op.alter_column(..., new_column_name=...)
  • 数据迁移——它只懂结构，不懂数据
  • 枚举类型变更——PostgreSQL 的 enum 改动不被完整支持
  • 部分索引、表达式索引——经常漏掉

这个项目的现状：env.py 目前是语法错误，跑不了

文件第 37–43 行长这样（原文照抄）：

这是把 .env 的内容粘进了 Python 文件，但没加引号。跑一遍语法检查，报错很明确：

14. 加一个完整功能的步骤清单

假设要加「文档上传」功能。严格按这个顺序走，每一步都能独立验证——这比一次写完再调试快得多。

第 1 步：模型

# app/models/document.py
from sqlalchemy import String, DateTime, func
from sqlalchemy.orm import Mapped, mapped_column
from app.db.base import Base

class Document(Base):
    __tablename__ = "documents"

    id: Mapped[int] = mapped_column(primary_key=True)
    title: Mapped[str] = mapped_column(String(200), index=True)
    cos_key: Mapped[str] = mapped_column(String(500), unique=True)
    created_at: Mapped[DateTime] = mapped_column(DateTime, server_default=func.now())

注意 Mapped[...] + mapped_column(...) 是 SQLAlchemy 2.0 的新风格：类型注解驱动。Mapped[str] 自动推导出 String，可空性也由 Mapped[str] 还是 Mapped[str | None] 决定，不用再写 nullable=True。

然后别忘了在 app/db/base.py 末尾 import 它（第 12 章讲过原因）。

第 2 步：验证映射能不能跑通（不要跳过）

uv run python -c "from app.db.base import Base; print(sorted(Base.metadata.tables))"

应该输出 ['documents']。

如果输出 []，说明 import 没生效。这时候去跑 autogenerate，会生成一个删掉数据库所有表的脚本。这一步 10 秒钟，能拦住一个灾难。

第 3 步：生成迁移并人工检查

uv run alembic revision --autogenerate -m "create documents"

打开生成的文件，确认 op.create_table("documents", …) 里的字段和模型一致。

第 4 步：应用迁移

uv run alembic upgrade head

第 5 步：Schema（出入参）

# app/schemas/document.py
from pydantic import BaseModel, ConfigDict

class DocumentOut(BaseModel):
    model_config = ConfigDict(from_attributes=True)
    id: int
    title: str
    cos_key: str

class DocumentCreate(BaseModel):
    title: str

from_attributes=True 让 Pydantic 能从 ORM 对象（而不是 dict）构造，这是 v2 的写法（v1 里叫 orm_mode）。

出入参一定要分成两个类。出参永远不该包含内部字段——否则某天你给模型加了个 internal_note 字段，它会自动出现在 API 响应里。这是典型的「无意泄露」。

第 6 步：Service（业务逻辑）

# app/services/document.py
async def create_document(session: AsyncSession, payload: DocumentCreate) -> Document:
    doc = Document(title=payload.title, cos_key=f"docs/{uuid4().hex}")
    session.add(doc)
    await session.commit()
    await session.refresh(doc)      # ← 因为 expire_on_commit=False
    return doc

refresh 不能省：expire_on_commit=False 意味着 commit 后对象不自动刷新，不 refresh 就拿不到数据库生成的 id 和 created_at。

第 7 步：路由

# app/api/routes/documents.py
router = APIRouter(prefix="/documents", tags=["documents"])

@router.post("", response_model=DocumentOut, status_code=201)
async def create(payload: DocumentCreate, session: DbSession) -> DocumentOut:
    doc = await document_service.create_document(session, payload)
    return DocumentOut.model_validate(doc)

路由里只做三件事：接参数、调 service、转输出。不写 SQL，不写业务分支。这样 service 可以脱离 HTTP 被单测。

第 8 步：挂载

# app/main.py
from app.api.routes import documents
app.include_router(documents.router, prefix="/api")

第 9 步：验证

uv run uvicorn app.main:app --reload --host 127.0.0.1 --port 8000

curl -X POST http://127.0.0.1:8000/api/documents \
     -H 'Content-Type: application/json' \
     -d '{"title":"测试文档"}'

再去 http://127.0.0.1:8000/docs 看一眼——新接口应该已经出现在 documents 分组下，而且响应模型渲染得很清楚。这是 FastAPI「自动文档」红利最直观的地方。

为什么必须「造完一层验一层」：这九步里任何一步错了，后面的报错都会指向别处。比如第 2 步没验，第 3 步生成的迁移会删表，第 4 步一跑数据库就空了——而下一层的报错只会说「表不存在」，让你查错方向。

15. 新手最常踩的坑

前四条是搭建这个骨架时真实踩到的，不是假设。后四条是同类项目的高频问题。

① 依赖名拼错，但安装「成功」了

pyproject.toml 里写的是 unicorn[standard]>=2.1.4——少了一个 v。

unicorn 在 PyPI 上真的存在：它是 Unicorn CPU 模拟器（QEMU 派生的指令级模拟引擎），跟 ASGI 服务器毫无关系。它不带任何命令行入口，所以 uv sync 一路绿灯，但 .venv/bin/ 里永远不会有 uvicorn：

error: Failed to spawn: `uvicorn`
Caused by: No such file or directory (os error 2)

排查顺序（记住这个顺序，能省很多时间）：

  1. 看项目 venv 的 bin/ 里有没有这个可执行文件
  2. 看 site-packages/ 里有没有这个包
  3. 最后才怀疑 PATH

而且这里还有连带的第二个坑：uvicorn 的版本号是 0.x，写 >=2.1.4 是不可满足的约束。所以改拼写时必须同时改版本号（本项目已修成 uvicorn[standard]>=0.53.0）。

② 模块级代码缩进断裂，属性「凭空消失」

config.py 里 cors_origins 和 cors_origin_list 掉到了类外面：

    @property
    def cos_configured(self) -> bool: ...

cors_origins: str = "http://localhost:5173"     # ← 顶格了，成了模块变量

@property                                        # ← 装饰在模块级函数上
def cors_origin_list(self) -> list[str]: ...

报错是：

AttributeError: 'Settings' object has no attribute 'cors_origin_list'

为什么会这样：@property 装饰在模块级函数上，产出的只是一个挂在模块上的 property 对象（永远不会被触发）。Settings 类里根本没有这个属性。

一行定死的方法——别靠肉眼，靠运行时断言：

from app.core import config as c
print([n for n in vars(c.Settings) if not n.startswith('_')])
print(hasattr(c.settings, 'cors_origin_list'))

输出 ['model_config', 'cos_configured'] 和 False——当场就能确认属性不在类里。

这类「作用域错位」的错，IDE 不一定报，因为语法是完全合法的。这是它最阴的地方。

③ 函数名少一个词

main.py 调用 register_error_handlers(app)，而 error_handlers.py 里定义的是 register_exception_handlers。差一个 exception，直接 AttributeError。

30 秒的防御手段——给每个模块写一个 import 冒烟测试：

# tests/test_imports.py
import importlib

def test_all_modules_import():
    for m in ["app.main", "app.core.config", "app.core.logging",
              "app.core.exceptions", "app.db.base", "app.db.session",
              "app.api.deps", "app.api.error_handlers",
              "app.api.routes.health", "app.storage.cos_client"]:
        importlib.import_module(m)

这一个测试能筛掉一整类「名字对不上 / 循环依赖 / 语法错」的问题，成本几乎为零。搭骨架阶段最该先写的就是它。

④ 把配置粘进 Python 文件，忘了引号

alembic/env.py 里那段 COS_SECRET_ID = AKID…。症状是 SyntaxError，报错位置指向行号，但问题往往出在上一行的变量名或上下文。

预防：提交前跑一遍全量语法检查。

uv run python -m compileall -q app alembic && echo "语法 OK"

（注意 compileall 会生成 __pycache__/，所以 .gitignore 得先写好。）

⑤ 端口在监听，但客户端连不上

uvicorn --host 127.0.0.1 只绑 IPv4 回环。macOS 上 localhost 同时解析出 ::1 和 127.0.0.1，如果某个客户端只试 IPv6，就会连不上而报「拒绝连接」。

lsof -nP -iTCP:8000 -sTCP:LISTEN     # 看它到底监听在哪个地址

要同时收 IPv6 用 --host ::，或用 --host 0.0.0.0 收所有网卡（后者局域网内其他机器也能访问，注意安全——这会顺带把你的开发接口暴露给同一网段的所有人）。

⑥ 浏览器把 http 自动升级成 https

现象：curl http://127.0.0.1:8000/docs 通，浏览器却报「此网站无法提供安全连接 / 发送的响应无效」。

机制：这是 ERR_SSL_PROTOCOL_ERROR。浏览器对纯 HTTP 的服务端做 TLS 握手，拿到一堆明文，握手失败。

怎么确认是它——能复现出一模一样的错误就说明对上了：

curl -k https://127.0.0.1:8000/docs

怎么排除代理干扰：

curl -x http://127.0.0.1:7897 http://127.0.0.1:8000/docs   # 走代理仍 200 → 不是代理问题

怎么修：地址栏显式写 http://；或在浏览器设置里关掉「始终使用安全连接」；或访问 chrome://net-internals/#hsts 删掉该域的安全策略。

顺带一个判断技巧：浏览器历史库里记录的 scheme 才是真相。地址栏输入过的 URL 会用 transition=1（TYPED）标记，页面真正渲染成功的话标题也会记下来——这两条信息足以区分「加载失败」和「加载成功」。

⑦ 改了代码但没生效

--reload 依赖 watchfiles，而它来自 uvicorn[standard] 这个 extra。如果装的是裸 uvicorn，热重载不会工作。

uv run python -c "import watchfiles; print(watchfiles.__version__)"

⑧ uv run 找不到命令 ≠ 命令不存在

uv run <cmd> 的查找顺序是：项目 venv 的 bin/ → 系统 PATH。它不会像 uvx 那样去下载。

所以「uv run 报找不到」时，该问的是「项目环境里到底装没装这个包」，而不是「我 PATH 是不是有问题」。

临时用一下但不想改依赖：

uv run --with some-package some-command

这个 --with 只对本次运行生效，不写进 pyproject.toml——非常适合验证性试跑。

结语

W1　这个骨架把「文件 / 元数据 / 向量」分别放在哪里？为什么说这是「决定了后面所有分层方式」的取舍？

查看参考答案

文件进 COS（原始 PDF / 文档不进数据库）、元数据进 PostgreSQL、向量进 pgvector。

之所以能决定分层：三类数据的访问方式完全不同——对象存储是「网络 IO + 同步 SDK」，关系库是「异步连接池 + ORM」，向量是「专门的类型与索引」。它们的生命周期、失败模式、性能特征都不一样，所以必须各有一个薄封装层，而不是混在一个「数据访问模块」里。

补充一句必须如实说明的：compose 起的是 pgvector/pgvector:pg16 镜像，说明计划把向量放这里，但代码里还没有任何模型或索引落地——目前只是选型就位。

查看参考答案

铁律：api → db / storage → core，core 绝不反向 import 任何上层。

后果有两条：① 形成循环依赖（api 依赖 core，core 又依赖 api）；② core 再也没法脱离 Web 框架单独测试——而它本来是最该被单独测试的部分。

验证命令：uv run python -c "from app.core import config; print(config.settings.app_name)"。能跑通说明 core 干净；报缺 fastapi 之类就说明地基里混进了上层依赖。

W3　以 GET /api/health/db 为例，说出从 uvicorn 到把 JSON 写回 socket 的完整链路（至少 6 个环节）。

查看参考答案

① 浏览器发 HTTP/1.1 GET /api/health/db；② uvicorn 把原始 socket 字节解析成 ASGI 的 scope + receive/send；③ Starlette 路由匹配，三层 prefix 拼出 /api + /health + /db；④ 依赖解析：看到 session: DbSession → Annotated[AsyncSession, Depends(get_session)] → 调用 get_session()；⑤ 进入 async with AsyncSessionLocal() as session，执行到 yield session，把 session 交给路由函数；⑥ health_db() 执行 await session.execute(text("SELECT 1"))；⑦ 返回 HealthStatus，按 response_model 校验后序列化成 JSON；⑧ get_session 的收尾：async with 退出 → session.close() → 连接归还池；⑨ uvicorn 把 JSON 字节写回 socket。

最容易被忽略的是第 ⑧ 步——它在响应发出之后才执行，这正是「一个请求一个 session，用完必定归还」的保证。

W4　app.main:app 里冒号前后分别是什么？敲下 uv run uvicorn app.main:app 时 uvicorn 实际做了哪三件事？app 是什么时候被创建的？

查看参考答案

冒号前是模块路径 app.main，冒号后是变量名 app。

W6　configure_logging() 里有四件「不这么做就会出问题」的事，分别是什么？get_logger 只有一行 return logging.getLogger(name)，为什么还要包这一层？

查看参考答案

四件事：① _configured 幂等闸——否则测试里连续建 10 个 app 就挂 10 个 handler，每条日志打印 10 遍；② root.handlers.clear()——保证「只此一个」输出口，避免重复打印；③ 接管 uvicorn 三个 logger——清掉它们自带的 handler 并设 propagate=True，否则 access log 和业务日志格式不一致；④ 输出到 sys.stdout——12-factor 惯例，日志不自己管文件轮转，交给容器 / 系统采集。

get_logger 是留接口：日后要换成 structlog、要注入 trace_id、要加敏感信息脱敏过滤器时，只要改这一个函数，全项目几十个调用点不用动。成本三行，收益是「未来某天的一次重构不用全项目替换」。

W7　AppException 的写法有四层讲究，分别是什么？两个 handler 的分工是什么？为什么注册顺序无关？

查看参考答案

四层讲究：① 用类属性承载默认值——子类只声明 code/message/http_status 就完成定制，完全不用写 __init__；② 用 if message is not None 而非 or——空字符串是合法输入；③ super().__init__(self.message)——让 str(exc) 有内容，否则 logger.exception 打出来是空白；④ 单独的 * 强制关键字传参——防止位置参数传错顺序。

分工：AppException 是「预料之内的错误」，业务代码主动抛，信息可以直接给用户看；Exception 是兜底的，绝不能把原始异常信息吐给客户端（可能含 SQL 语句、文件路径、连接串），只记日志、返回统一话术。兜底 handler 必须有——没有它，未捕获异常会让客户端收到 uvicorn 的纯文本 traceback。

注册顺序无关：add_exception_handler 是按类型精确匹配的，Starlette 会沿异常的 MRO 往上找注册过的 handler，所以 NotFoundException 自然命中 AppException 那一条。

W8　expire_on_commit=False 解决什么问题、代价是什么？get_session 的三个层次分别是什么？

查看参考答案

解决的问题：commit 后如果对象字段被标记为过期，再读属性会触发新的 SELECT（隐性 N+1），异步下还可能报 MissingGreenlet。

代价：commit 之后对象里的数据是快照，不再自动从库刷新。依赖「commit 后重新读能拿到数据库算出来的值」（触发器改的字段、自增主键）时，要手动 await session.refresh(obj)。

get_session 的三层：① async with 保证无论正常返回还是抛异常，session 一定会关闭（注意归还的是连接池里的连接，不是关掉 TCP）；② yield 把它变成 FastAPI 的生成器依赖——请求进来前执行 yield 之前，响应发出后执行 yield 之后；③ AsyncGenerator[AsyncSession, None] 的类型注解，让 DbSession 那个 Annotated 能推导出正确类型。

W9　DbSession = Annotated[AsyncSession, Depends(get_session)] 把哪三层缝在了一起？FastAPI 拿到它会自动做哪三步？Annotated 相对 = Depends(...) 的优势是什么？

查看参考答案

缝起三层：类型（AsyncSession）+ 注入指令（Depends(get_session)）+ 一个可复用的名字（DbSession）。

FastAPI 自动三步：① 调用 get_session() 拿到生成器；② 进场（执行到 yield），把 yield 出来的 AsyncSession 塞进参数；③ 函数执行完，退场（继续执行 yield 之后的清理代码）。

Annotated 的优势：把「类型」和「注入指令」合并到一个名字里。没有它就得写 session: AsyncSession = Depends(get_session)——默认值的位置被占用了（这个参数再也没法有别的默认值），而且每个调用点都要重复写一遍完整表达式。

更本质地说，这是「依赖倒置」的落点：路由依赖抽象（DbSession 这个名字），不依赖具体构造方式。

W10　cos_client.py 的三个关键决策是什么？「依赖的失败不应该阻止进程启动」在这份代码里怎么体现、为什么要这么做？

查看参考答案

三个决策：① 用 asyncio.to_thread 包同步 SDK——腾讯云 SDK 内部走 requests，会阻塞线程，在 async 函数里直接调会卡住整个事件循环；② 懒加载 + 模块级单例——第一次调用 get_cos_client() 时才真正构造；③ 构造失败抛项目自己的 ConfigurationError——它会被全局 handler 转成 503 + {"code":"configuration_error"}，前端能识别；抛裸的 RuntimeError 就只能落进 500 兜底。

体现：懒加载让进程启动时不连 COS。密钥填错或网络不通时，服务照样能起来，只是 /health/cos 报 error——而不是整个后端起不来。理由：一个次要依赖抖动不应该引发服务雪崩。

W11　三个探针端点分别探什么？各自挂了意味着什么？为什么 liveness 和 readiness 必须挂不同端点？

查看参考答案

/api/health：探「进程活着、能返回响应」，挂了＝进程死了或端口不通。关键：它不碰任何外部依赖。

/api/health/db：真发一条 SELECT 1，挂了＝数据库不可用或连接串配错。/api/health/cos：真做一次 head_bucket，挂了＝密钥错 / 桶不存在 / 网络不通。

正确的挂法：liveness → /health（别让数据库抖动把好 Pod 杀掉重启）、readiness → /health/db（依赖没好就不接流量）。混成一个端点会导致「数据库慢 → Pod 被判定死亡 → 重启 → 数据库更慢」的死亡螺旋。

W12　env.py 里真正重要的只有两行，分别是什么、各解决什么问题？由此产生什么硬依赖？--autogenerate 在哪些场景下会出错？

查看参考答案

① config.set_main_option("sqlalchemy.url", settings.database_url)——把连接串从 Settings 取过来覆盖 alembic.ini 里的。这样数据库地址只有一个来源（.env），不会出现「应用连 A 库、迁移改 B 库」的事故。② target_metadata = Base.metadata——--autogenerate 的对照基准。

硬依赖：必须让 env.py import 到所有模型。否则 Base.metadata 里没有你的表，autogenerate 会生成一个「删掉所有表」的脚本——这是 Alembic 最危险的事故。标准做法是在 app/db/base.py 末尾集中 import。

出错场景：字段重命名（被当成「删一个、加一个」，数据全丢，必须手改成 op.alter_column(..., new_column_name=...)）、数据迁移（它只懂结构不懂数据）、枚举类型变更（PG 的 enum 改动不被完整支持）、部分索引 / 表达式索引（经常漏）。

另外别忘了为什么 env.py 必须是 async 版本：驱动是 asyncpg，同步 Alembic 连不上 postgresql+asyncpg://。

W14　说出加一个功能的九步顺序。为什么必须「造完一层验一层」？第 2 步具体在验什么、验不过会导致什么？

W15　从 8 个坑里挑出搭建这个骨架时真实踩到的那 4 个，说出各自的症状与修法。

查看参考答案

① 依赖名拼错，但安装「成功」了。症状：uv run uvicorn 报 Failed to spawn: uvicorn / No such file or directory。原因：unicorn 是 PyPI 上真实存在的另一个包（Unicorn CPU 模拟器），不带命令行入口。修法：改成 uvicorn[standard]，版本号要一起改（uvicorn 是 0.x，>=2.1.4 不可满足）。

② 模块级代码缩进断裂，属性「凭空消失」。症状：AttributeError: 'Settings' object has no attribute 'cors_origin_list'。原因：cors_origins 和 @property cors_origin_list 掉到类外面，@property 装饰在模块级函数上产出的只是挂在模块上的 property 对象。修法：整体缩进收进 Settings 类（@lru_cache 那两行保持模块级）。判据：vars(Settings) + hasattr(settings, 'cors_origin_list')，别靠肉眼。

③ 函数名少一个词。症状：AttributeError。原因：main.py 调 register_error_handlers，实际定义是 register_exception_handlers。修法：改对名字，并加一个 import 冒烟测试（tests/test_imports.py 用 importlib 逐个 import 10 个模块），一次筛掉整类「名字对不上 / 循环依赖 / 语法错」的问题。

④ 把配置粘进 Python 文件，忘了引号。症状：SyntaxError: invalid syntax（alembic/env.py line 41），报错位置指向行号，但问题往往出在上下文。修法：删掉那几行（配置走 settings 已经有了，不需要重复），并把明文密钥移到 .env。预防：提交前跑 uv run python -m compileall -q app alembic。
